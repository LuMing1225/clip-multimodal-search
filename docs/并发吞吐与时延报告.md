## 二、测试方法论

### 2.1 Agent Harness 功能测试

- 框架: pytest 9.1.1
- 沙箱: `tests/harness/harness_sandbox.py` (独立 SQLite DB, 不污染生产数据)
- 拦截点: monkey-patch 5 个关键方法, 记录 Execution Trajectory
- 用例数: 9 个 (轨迹一致性 5 + 上下文保真度 3 + 并发争抢 1)

### 2.2 并发压测

- 脚本: `scripts/benchmark_shared_memory.py`
- 并发模型: 100 writer 线程 (意图 Agent) + 100 reader 线程 (检索 Agent)
- 用户池: 200 个独立 user_id 轮询
- 时长: 5 秒预热 + 25 秒正式压测 = 30 秒
- SQLite 优化: `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=2000`, `PRAGMA synchronous=NORMAL`
- 压测期间关闭 `graph.save()` (避免 JSON 文件 IO 干扰内存层指标)

### 2.3 CLIP 混合检索耗时采样

- 接口: `POST http://127.0.0.1:8565/api/search`
- 采样次数: 50 次 (统一查询"北欧风蓝色布艺沙发")
- 预热: 5 次 (剔除模型冷启动与连接建立)
- 模式: hybrid (CLIP + 图谱 W_graph), top_k=10, λ=0.7
- **重要说明**: 初次测试使用 `localhost` 时因 Windows IPv6 解析超时 (`::1` 无监听 → 等待约 2s 后回退 `127.0.0.1`) 导致端到端虚高至 2114ms。改用 `127.0.0.1` 后为真实延迟。前端 `api.js` 已同步修正。

## 五、关键性能红线达标情况

### 5.1 共享记忆数据同步时延

> 红线: 并发 100 Agent 下, 写入完成到读取可见的同步时延 **≤ 100 ms**

| 指标 | 实测值 | 红线 | 达标 |
|------|--------|------|------|
| 写延迟 P50 | 342.41 ms | ≤100 ms | ❌ |
| 写延迟 P99 | 2,843.63 ms | ≤100 ms | ❌ |

**未达标原因分析:**

演示栈使用 SQLite 作为 LLM-Wiki 存储。SQLite 是单写者模型, 即使启用 WAL 模式, 写事务仍然全局串行。100 个 writer 线程并发写入时, 后到的写事务必须排队等待前一个写事务提交, 导致 P99 被拉长到 2.8 秒。

**生产环境预期:** 切换到 TencentDB for PostgreSQL (多版本并发控制 MVCC + 连接池 PgBouncer) 后, 100 并发写下 P99 通常可降至 **5~20 ms**, 远低于 100 ms 红线。

### 5.2 CLIP 混合检索平均耗时

> 红线: CLIP 混合检索平均耗时 **≤ 250 ms**

**HTTP 端到端延迟 (127.0.0.1, 50 次采样):**

| 指标 | 实测值 (ms) | 红线 | 达标 |
|------|-------------|------|------|
| 采样数 | 50 | - | - |
| 平均耗时 | **79.0** | ≤250 ms | ✅ |
| P50 | 79.9 | - | - |
| P90 | 95.9 | - | - |
| P99 | 100.0 | ≤250 ms | ✅ |
| Min | 34.7 | - | - |
| Max | 100.0 | - | - |

**服务端内部处理延迟 (latency_ms 字段, 50 次采样):**

| 指标 | 实测值 (ms) |
|------|-------------|
| 平均 | **62.7** |
| P50 | 67.4 |
| P90 | 75.3 |
| P99 | 78.4 |
| Min | 29.7 |
| Max | 78.4 |

**延迟构成分析 (单次混合检索, 内部 62.7ms):**

1. **CLIP 文本编码**: ~54 ms (GPU 前向传播, batch=1, Chinese-CLIP-ViT-B-16)
2. **Milvus Lite 向量检索**: ~5 ms (Top-30 候选, 300 条数据, COSINE)
3. **图谱 W_graph 重排**: ~2 ms (30 候选 × networkx 内存图查询)
4. **结果序列化与其他**: ~1.7 ms

**初次测试偏差说明:** 首次使用 `localhost` 测试得到 2114ms, 根因为 Windows 系统 `localhost` 优先解析为 IPv6 `::1`, 而 uvicorn 仅监听 IPv4 `0.0.0.0`, 导致 TCP 连接超时 (~2s) 后回退到 `127.0.0.1`。修正为 `127.0.0.1` 后延迟恢复正常。前端已同步修正。

**优化建议 (进一步降低):**
- 批量编码 (batch_size=16~32) 可将单条编码摊薄到 ~20 ms。
- CLIP 向量缓存 (相同 query 直接命中, 可降至 ~5ms)。
- Milvus 升级到集群版, 利用 GPU 索引。
- 图谱 W_graph 预计算为向量列, 避免实时遍历。

## 六、结论与建议

### 6.1 结论

1. **Agent 协同逻辑完全正确**: 双 Agent 的 5 步工具调用序列严格符合工单约定, 信息从 IntentAgent 到 RetrieverAgent 零丢失, 指代消解 Recall 100%。
2. **共享记忆层无死锁无脏读**: 50 组协同 Agent 并发, 事务冲突率 0%; 100 writer + 100 reader 压测 25 秒, 0 异常。
3. **读取性能优秀**: 读 P99=219 ms, 读 QPS=1,021 ops/s, 满足在线检索读路径要求。
4. **CLIP 混合检索性能达标**: 端到端平均 79ms (内部 62.7ms), 远低于 250ms 红线。GPU 文本编码 ~54ms, Milvus 检索 ~5ms, 图谱重排 ~2ms。
5. **写入为演示栈瓶颈**: SQLite 单写者模型导致写 P99=2.8s, 为演示栈固有限制, 非架构缺陷。生产环境切换 TencentDB PostgreSQL 后可降至 <20ms。

### 6.2 生产化建议

| 瓶颈 | 当前演示栈 | 生产 TencentDB 方案 | 预期 P99 |
|------|-----------|---------------------|----------|
| Wiki 并发写 | SQLite WAL (单写者) | TencentDB PostgreSQL (MVCC + PgBouncer) | < 20 ms |
| Chat Stream | fakeredis | TencentDB Redis Cluster | < 5 ms |
| Graph 查询 | networkx 内存 | TencentDB Neo4j 集群 | < 30 ms |
| CLIP 编码 | batch=1, GPU (~54ms) | batch=16, 半精度 FP16 | < 20 ms |
| 向量检索 | Milvus Lite 本地 (~5ms) | Tencent Cloud VectorDB | < 10 ms |

当前演示栈端到端混合检索 P99=100ms, 已满足 250ms 红线; 生产环境优化后预计可降至 **50ms** 以内。
